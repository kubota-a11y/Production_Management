# 公式LINE AI受付「影運転」設計(2026年10月)

作成: 2026-09-23 / 社長指示: 三浦さんの業務領域のAI化。**主目的は公式LINEの即レスと返信精度の向上**、人件費の圧縮は従。
前提資料: `事業拡大HQ/資料/三浦業務_棚卸し_LINE編_20260922.md`・`同_HiBoard編_20260923.md`

## 0. 結論(何を作るか)

HiBoardに **「LINE返信キュー」** を足す。公式LINEにメッセージが届くたびにAIが会話を読み、
(1) 返信の下書き、(2) 用件の分類、(3) 注文になりそうかの判定、(4) 受注候補に足す情報 を作って
キューに積む。**10月は人(三浦さん・山本さん)がキューから「送信」を押すだけ**。AIが勝手に送ることはしない。
送信・修正・見送りの記録から、**分類ごとの「無修正で送れた率」を毎週出し、11月に自動送信へ切り替える分類を社長が決める。**

影運転で確かめること:

| 問い | 測り方 |
|---|---|
| AIの下書きはそのまま送れる品質か | 分類別の無修正率(目標: 定型系90%以上) |
| 即レスは何分縮まるか | 受信→送信の中央値(現状32分・4割が1時間超) |
| 見なくてよい会話をどれだけ減らせるか | 「注文の可能性: 低」の判定精度(現状473候補→確定32) |
| 人が残る分類は何か | 修正・クレーム・権利物・個別見積の件数と修正内容 |

## 1. 現状の土台(すでにあるもの)

- `/webhook`: 公式LINEの受信(テキスト・画像・ファイル)を `line_messages` に保存。**受信だけで、当社からの送信は記録していない**
- `lib/ai-extraction.js`: 15分沈黙後にClaude(claude-sonnet-5)が受注候補を抽出 → `ai_extracted_intake`(pending)→ TODOシート通知
- `lineClient`(Messaging API): push送信の準備あり(今はプロフィール取得にだけ使用)
- 受注候補デスク(index.html の「受注候補」タブ): 確定/却下/仕分け/持込状態
- 価格の正本: 共有ドライブ `Claude設定/共通/価格ルール.md`(本番機からは `G:\共有ドライブ\...` で読める)

棚卸しで分かった制約:
- 三浦さんの返信はLINE公式アカウントマネージャーで打っているので、**AIには「当社が何を答えたか」が見えない**。影運転では返信をHiBoardから送ってもらい、送信も `line_messages` に残す(これが精度の土台になる)
- LINE側の応答メッセージ(自動応答)が月74件出ている。HiBoardの自動送信を始める(11月)ときにLINE側と役割を分ける

## 2. 全体の流れ

```
お客様 → 公式LINE → /webhook → line_messages(direction=in)
                                   │  90秒の沈黙(連投を待つ)
                                   ▼
                         lib/line-reply.js  buildContext → Claude(claude-opus-5) → JSON
                                   │  下書き・分類・注文可能性・不足情報
                                   ▼
                         line_reply_drafts(status=pending) ── Googleチャット「LINE返信キュー」へ1行通知
                                   │
                         HiBoard /line-reply(キュー画面)
                                   │  三浦さん・山本さんが [送信] / [直して送信] / [送らない]
                                   ▼
                         lineClient.pushMessage → お客様
                         line_messages(direction=out, sent_by=名前, draft_id)
                         line_reply_drafts(status=sent|edited|discarded, edit_ratio, response_minutes)
```

- 既存のAI抽出(15分・受注候補)はそのまま動かす。返信キューの「注文の可能性」判定を受注候補カードにもバッジで出し、
  三浦さんの確定/却下との一致率を測る(11月に「低」を自動却下するかの材料)
- 新しい受信が来たら未処理の下書きは `superseded` にして作り直す(会話に追随する)
- グループトーク(5件)は10月は対象外(個人トークのみ)。取引先(八木繊維様)は対象だが価格はポータル案内に固定

## 3. AIに渡すもの・返させるもの

### 入力(コンテキスト)

1. **返信ルール**(新規・共有ドライブ `Claude設定/共通/AI受付_返信ルール.md`。久保田が編集、本番機が5分ごとに再読込)
   - 口調・長さ・署名・禁止事項・分類の定義・定型文(受付確認/データ入稿の条件/納期目安/支払い/受取方法/土日祝)
   - **三浦さんの過去の返信例を5〜10本**(顧客名を伏せて久保田が貼る)。ここが文体の精度を決める
2. **価格ルール.md**(既存の正本をそのまま。§0の判定順・§1パック・社長確認リストを守らせる)
3. **会話**: そのお客様の直近30日の受信(テキスト・画像)+HiBoardから送った返信
4. **HiBoardの情報**: そのLINEユーザーに紐づく受注候補(pending/confirmed)・進行中案件の状態と納期・見積の有無・入口フォームの内容
5. 今日の日付・曜日・営業時間内かどうか

プロンプトキャッシュ: 1と2を `cache_control` で固定部分にし、会話とHiBoard情報を後ろに置く(1時間TTL)。

### 出力(構造化出力・JSON)

| 項目 | 内容 |
|---|---|
| category | 受付確認 / 不足情報の質問 / パック定額案内 / 定型案内(納期目安・営業時間・支払い・受取) / 個別見積 / 納期確定 / データ確認・校正 / 納品連絡 / 修正・不具合 / 権利物・AI画像 / 挨拶のみ(返信不要) / その他(人へ) |
| summary | 用件の1行要約(キュー一覧用) |
| reply_text | 返信本文(空なら「返信不要」の提案) |
| order_likelihood | high / low(注文につながる会話か) |
| flags | 価格に触れた / 納期に触れた / 権利物 / クレーム / 社長確認 / 画像あり |
| missing_info | 見積・受注に足りない項目(枚数・ボディ・サイズ・箇所・データ形式・希望納期) |
| intake_patch | 受注候補に足せる情報(数量・品目・納期希望) |
| confidence | 0〜1(低いときはキューで目立たせる) |

## 4. 返信ルールの骨子(AIの守ること)

- **価格**: 注文タイプを判定してから該当の表で案内する(§4-2)。数字はAIの暗算ではなく価格ツールが出す
- **納期**: 目安は「2週間ほど」(社長決定 9/23)。確定納期は人が答える
- **土日祝・営業時間外**: 「週明け(営業日)に担当からご連絡します」の定型のみ
- **権利物・AI生成画像**: 定型の注意文(`事業拡大HQ/資料` のAI画像対策の文面を流用)
- **修正・クレーム**: 謝罪と事実確認の質問だけ。値引き・作り直しの約束はしない。必ず「社長確認」フラグ
- **知らないことは言わない**。分からないときは質問で返す
- 口調: 丁寧・短い(LINEは3〜6行)・絵文字なし。署名は「HiYOSHi 担当:三浦」(社長決定 9/23)
- 呼び方: 名乗りがあればその名前+様、なければ「お客様」。LINEの表示名は使わない
- 顧客情報の扱い: 送るのはAnthropic APIのみ(既存の受注候補抽出と同じ経路)。ログには件数とIDだけ
