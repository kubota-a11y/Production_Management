# HiBoard サーバー機 移行手順(現メイン機 → 新サーバー専用機)

三浦さんが Illustrator 等の実務で使っているメインPCが、同時に HiBoard の本番サーバーも兼ねている状態を解消し、
**サーバー専用のWindows機へ引っ越す**ための手順書。

## なぜ分けるのか

現状は「メインPCが止まると、社内の案件管理だけでなく**お客様向けの公開注文フォームまで落ちる**」構成になっている。
実務PCは Illustrator の再起動・アプリの不調・電源オフが日常的に起きるため、サーバーを分離すると次の効果がある。

- 三浦さんが自由にPCを再起動・シャットダウンできる
- 公開フォーム(`order.kubota-tunnel.com`)と選手応援サイト(`genpei-hayashi.com`)が24時間安定する
- サーバー機は無人運用に振り切れる(自動ログオン・スリープ無効・Windows Update時間帯の固定)
- Illustrator の重い処理とサーバー処理が競合しなくなる

---

## 0. 全体像とスケジュール感

| フェーズ | 内容 | 業務への影響 | 目安 |
|---|---|---|---|
| フェーズ1 | 新PCの下地づくり(Windows設定・Node.js・Git・NAS) | なし。旧サーバーは動いたまま | 1〜2時間 |
| フェーズ2 | HiBoard の設置と単体動作確認(テストデータで) | なし | 1時間 |
| フェーズ3 | Cloudflare Tunnel の移設準備 | なし | 30分 |
| フェーズ4 | **本番切り替え**(DBコピー＋トンネル切替) | **公開フォームが5〜10分停止** | 15分 |
| フェーズ5 | 切り替え後の確認 | なし | 30分 |
| フェーズ6 | 旧PCの後片付け(1〜2週間の安定稼働を確認してから) | なし | 15分 |

> **フェーズ1〜3は業務時間中にやってよい。** 旧サーバーは動き続けるので、失敗しても何も壊れない。
> **フェーズ4だけ営業時間外(夕方以降・休業日)に行う。** 注文フォームが数分止まるため。

## 新PCの推奨スペック(参考)

HiBoard は Node.js + SQLite の軽量アプリで、社内数名＋公開フォームのアクセス規模なら要求は低い。

| 項目 | 目安 | 理由 |
|---|---|---|
| CPU | 現行世代の Core i3 / Ryzen 3 以上 | 十分。ハイスペックは不要 |
| メモリ | 8GB(16GBあれば安心) | |
| ストレージ | SSD 256GB以上 | HDDは避ける(DBの書き込みが遅く、故障リスクも高い) |
| 本体 | 小型デスクトップ(ミニPC/NUC等) | 24時間通電するので省電力・静音が有利。ノートPCはバッテリー劣化・蓋閉じスリープの管理が面倒 |
| ネットワーク | **有線LAN** | 無線は切断リスクがある。公開サイトの配信元なので有線必須 |
| OS | Windows 11 Pro | Home でも動くが、Pro のほうが自動ログオン等の設定がしやすい |

**あると良いもの: UPS(無停電電源装置)。** 停電時に SQLite の書き込み中に電源が落ちるとDB破損の可能性がある。
1万円台の小型UPSでも「数分間持たせて安全にシャットダウンする」効果があり、本番機には有効。

## フェーズ0: 旧PC(現メイン機)で控えておく情報

切り替え作業を始める前に、旧PCで以下を確認してメモしておく。**このメモはチャットやメールに貼らないこと**(認証情報が混ざる)。

```bat
node -v
npm -v
git --version
ipconfig
```

| 控える項目 | 確認方法 | 使いどころ |
|---|---|---|
| Node.js のバージョン | `node -v` | 新PCも同じメジャーバージョンのLTSを入れる(better-sqlite3 / sharp のビルド互換のため) |
| 旧PCのIPアドレス | `ipconfig` の IPv4 アドレス | 新PCに**同じIPを引き継ぐ**と社員側のブックマーク変更が不要 |
| NASの割り当てドライブ | エクスプローラーで確認(通常 `Z:`) | 新PCも同じドライブレターにする |
| Windowsのログオンアカウント名 | `whoami` | タスクスケジューラの `/ru` に使う |
| cloudflared の管理方式 | 下記フェーズ3で判定 | トンネル移設の方法が変わる |

さらに、以下のファイル・フォルダをUSBメモリにコピーしておく(**社長ご自身の手作業**。私は本番の `.env` と `projects.db` には触れません)。

1. `C:\Production_Management_v2\.env` ← SMTP・TODOシート連携・NASパス・APIキー等が入った最重要ファイル
2. `C:\Production_Management_v2\db\backups\` ← 直近のバックアップ一式(保険)
3. `%USERPROFILE%\.cloudflared\` フォルダ(存在する場合。フェーズ3で使う)

> **USBメモリは作業後に必ず回収・データ削除する。** `.env` には SMTP パスワードや各種トークンが平文で入っている。

## フェーズ1: 新PCの下地づくり

### 1-1. Windows の基本設定(サーバー専用機として)

| 設定 | 場所 | 設定値 |
|---|---|---|
| スリープ無効 | 設定 → システム → 電源 | 「スリープ状態にする」= **なし**(画面オフはOK) |
| 高速スタートアップ無効 | コントロールパネル → 電源オプション → 電源ボタンの動作 | チェックを外す(再起動時の挙動を素直にする) |
| Windows Update のアクティブ時間 | 設定 → Windows Update → 詳細オプション | 業務時間内に自動再起動しないよう時間帯を指定 |
| コンピューター名 | 設定 → システム → バージョン情報 | 分かりやすい名前に(例: `HIBOARD-SERVER`) |
| 固定IP または DHCP予約 | ルーター側の予約が簡単 | **旧サーバー機と同じIPにできれば理想** |

### 1-2. 自動ログオンの設定(サーバー専用機だからこそ推奨)

HiBoard の常駐方式はタスクスケジューラの**「ログオン時」トリガー**。つまり **PC再起動後に誰かがログオンしないとサーバーが起動しない**という弱点がある。
サーバー専用機なら自動ログオンを設定しておくと、Windows Update等で再起動しても無人で復帰する。

1. `Win + R` → `netplwiz` → Enter
2. 「ユーザーがこのコンピューターを使うには、ユーザー名とパスワードの入力が必要」の**チェックを外す**
   - この項目が表示されない場合は、レジストリで `DevicePasswordLessBuildVersion` を `0` にすると現れる
3. 「適用」→ 自動ログオンさせるアカウント名とパスワードを入力

> **セキュリティ上の判断:** 自動ログオンは「PCの前に座れば誰でもデスクトップが見える」状態になる。
> サーバー機を施錠された場所・関係者しか入らない場所に置くこと。持ち出す機体では設定しない。
> 気になる場合は自動ログオンを使わず、「再起動後は誰かが一度ログオンする」運用でも構わない。

### 1-3. NAS(LAN DISK)の接続

1. 新PCに **LAN DISK Connect** をインストール(SMB直接接続ではなくこのツール経由が現行の運用)
2. NASを **旧PCと同じドライブレター(通常 `Z:`)** で割り当てる
3. 「ログオン時に再接続する」を有効にする
4. エクスプローラーで `Z:\DESIGN` に実際に入れることを確認する

> **重要:** HiBoard は NAS を4か所で使う(デザインデータ閲覧・Web注文画像の保存・取引先加工依頼画像の保存・DBバックアップのNAS二重保存)。
> ドライブレターが旧PCと違うと `.env` の書き換えが必要になるので、**同じレターに揃えるのが一番楽**。

### 1-4. Node.js と Git のインストール

1. [https://nodejs.org](https://nodejs.org) から **LTS版の .msi** をダウンロードして実行
   - フェーズ0で控えた旧PCのバージョンと同じメジャーバージョンを選ぶ
2. [https://git-scm.com/download/win](https://git-scm.com/download/win) から Git for Windows をインストール(既定設定でよい)
3. 確認

```bat
node -v
npm -v
git --version
```

## フェーズ2: HiBoard の設置と単体動作確認

### 2-1. リポジトリを取得

```bat
cd C:\
git clone https://github.com/kubota-a11y/Production_Management.git Production_Management_v2
cd C:\Production_Management_v2
```

> GitHub の認証を求められたら、Git Credential Manager のブラウザ認証でGitHubアカウントにログインする。
> **フォルダ名は `Production_Management_v2` にすること**(`update.bat` やドキュメントがこのパス前提で書かれている)。

### 2-2. 依存パッケージのインストール

```bat
npm install
```

`better-sqlite3` と `sharp` はネイティブモジュールなので、ここで Windows 用のバイナリが用意される。
`node-gyp` / `python` 関連のエラーで失敗する場合は、Node.js を LTS版に揃えるか、
[Visual Studio Build Tools](https://visualstudio.microsoft.com/downloads/#build-tools-for-visual-studio-2022) を「C++によるデスクトップ開発」付きで入れてから再実行する。

### 2-3. `.env` を配置

USBメモリからコピーした `.env` を `C:\Production_Management_v2\.env` として置く。
そのうえで、以下の項目だけメモ帳で開いて確認する(値の内容は変えず、パスの整合性だけ見る)。

| 項目 | 確認内容 |
|---|---|
| `NAS_BASE_PATH` | 新PCで割り当てたドライブレターと一致しているか |
| `WEB_ORDER_RECEIVED_PATH` | 同上 |
| `PARTNER_ORDER_RECEIVED_PATH` | 同上 |
| `DB_BACKUP_EXTRA_DIR` | 同上(NAS側のバックアップ先) |
| `PORT` | `3000` のまま |
| `PUBLIC_ORDER_BASE_URL` / `PUBLIC_HOSTNAMES` | 公開ドメインは変わらないので**そのまま**。書き換え不要 |
| SMTP・TODOシート・LINE・各種トークン | **そのまま。触らない** |

### 2-4. テストデータで起動確認(まだ本番DBは持ってこない)

この時点では本番DBを入れない。空のDBが自動生成されるので、それで動作確認する。

```bat
npm start
```

- ログに「サーバー起動」と表示され、`http://localhost:3000` で案件一覧が開くこと
- 初回起動時にファイアウォールのダイアログが出たら「**プライベートネットワーク**」にチェックして「アクセスを許可する」
  - ダイアログを取り逃した場合: 「Windows Defender ファイアウォールを許可されたアプリ」→ 設定の変更 → 別のアプリの許可 → `C:\Program Files\nodejs\node.exe` を追加し「プライベート」にチェック
- LAN内の別PC・スマホから `http://<新PCのIP>:3000` が開けること
- **NASが見えること** — 「➕ 新規案件」→「NASデザインフォルダパス」の「📁 参照...」でフォルダ一覧が出ればOK(案件は登録せず閉じる)

確認できたら `Ctrl + C` でいったん止める。

### 2-5. 常駐化(タスクスケジューラ)の設定

`docs\Windowsサービス化手順.md`「方法A」と同じ内容。**管理者ターミナル**で実行する。

**PowerShell の場合:**

```powershell
schtasks /create /tn "HiBoard" /tr "C:\Production_Management_v2\run-server-loop.bat" /sc onlogon /ru "$env:USERNAME" /f
```

**コマンドプロンプトの場合:**

```bat
schtasks /create /tn "HiBoard" /tr "C:\Production_Management_v2\run-server-loop.bat" /sc onlogon /ru "%USERNAME%" /f
```

> **絶対にやらないこと: `/rl highest`(最上位の権限)を付けない。**
> 管理者権限のプロセスからは通常ユーザーが割り当てた `Z:` ドライブが見えなくなり、NAS機能が全部壊れる。
> 同じ理由で **NSSM / Windowsサービス化は使わない**(HiBoard に限った話。cloudflared は後述のとおりサービスでよい)。

作成できたら、実行ユーザーが普段のアカウントになっているか確認する。

```bat
schtasks /query /tn "HiBoard" /v /fo list
```

起動テストと自動復活テスト:

```bat
schtasks /run /tn "HiBoard"
```

「生産管理サーバー (自動再起動あり)」ウィンドウが開き、`http://localhost:3000` が開けること。
タスクマネージャーで `node.exe` を「タスクの終了」した5秒後に自動で復活すればOK。

## フェーズ3: Cloudflare Tunnel の移設準備

公開URL(`order.kubota-tunnel.com`・`genpei-hayashi.com`)と LINE Webhook は、
**`hiyoshi-line-webhook` という名前の Cloudflare Tunnel** 経由で旧PCの `localhost:3000` に届いている。

### 方針: 新しいトンネルを作らず、同じトンネルを新PCで動かす

同じトンネルを引き継げば、以下が**すべて変更不要**になる。ここが今回の移行を簡単にする最大のポイント。

- DNSレコード(order.kubota-tunnel.com / genpei-hayashi.com / www)
- LINE Developers 側の Webhook URL
- Cloudflare Turnstile(ボット対策)のサイト設定
- お客様に配布済みの注文フォームURL・QRコード
- 発行済みのトークン別URL(`/team/{token}` `/partner/{token}` `/designer/{token}`)

### 3-1. 現在の管理方式を判定する(旧PC)

旧PCで、エクスプローラーのアドレス欄に `%USERPROFILE%\.cloudflared` と入れて開く。

| 見えるもの | 管理方式 | 進む先 |
|---|---|---|
| `config.yml` と `<長いUUID>.json` がある | **ローカル設定ファイル方式** | 3-2A |
| フォルダが無い / `.json` だけ | **ダッシュボード(リモート)管理方式** | 3-2B |

### 3-2A. ローカル設定ファイル方式の場合

1. 旧PCの `%USERPROFILE%\.cloudflared\` フォルダを**丸ごと**USBメモリにコピー
   (`config.yml` / `<UUID>.json` / `cert.pem`)
2. [https://github.com/cloudflare/cloudflared/releases](https://github.com/cloudflare/cloudflared/releases) から
   `cloudflared-windows-amd64.msi` を新PCにインストール
3. コピーしたフォルダを新PCの `%USERPROFILE%\.cloudflared\` に置く
4. `config.yml` をメモ帳で開き、`credentials-file:` に書かれたパスが**新PCの実際のパス**になっているか確認する
   (旧PCのユーザー名が入っていたら新PCのユーザー名に直す)
5. **この時点では起動しない。** フェーズ4の切り替え時に起動する

### 3-2B. ダッシュボード管理方式の場合

1. [https://one.dash.cloudflare.com](https://one.dash.cloudflare.com) にログイン
2. 「Networks」→「Tunnels」→ `hiyoshi-line-webhook` を選択
3. 「Configure」→「Install and run a connector」の **Windows用インストールコマンド**をコピー
   (`cloudflared.exe service install <長いトークン>` の形)
4. **この時点では実行しない。** フェーズ4の切り替え時に新PCで実行する
5. 同じ画面の「Public Hostname」タブで、現在の設定を**スクリーンショットに撮っておく**
   (`order.kubota-tunnel.com` → `http://localhost:3000` などの対応表。万一のときの復元用)

> **cloudflared は Windowsサービスとして入れてよい。** HiBoard 本体と違って NAS を触らないため、
> LocalSystem で動いても問題は起きない。むしろサービスのほうがログオン前から動いて安定する。

## フェーズ4: 本番切り替え(営業時間外に実施・所要15分)

ここからが実際の切り替え。**この間、公開注文フォームが5〜10分停止する。**
上から順にそのまま実行すれば完了する。

### 4-1. 旧PC: サーバーを停止する

```bat
schtasks /end /tn "HiBoard"
taskkill /F /IM node.exe
```

> 自動再起動の仕組み(タスク)ごと止めないと、`node.exe` を消しても5秒後に復活してしまうので順番が大事。
> 「生産管理サーバー (自動再起動あり)」ウィンドウが残っていたら閉じる。

### 4-2. 旧PC: 整合性のあるDBコピーを作る

**稼働中の `projects.db` を単純にコピーしてはいけない。** WALモードで動いているため、
`projects.db-wal` に未反映の書き込みが残っていて、`.db` 単体をコピーすると**直近の案件が欠ける**。
専用スクリプトを使えば整合性のあるコピーが作れる。

```bat
cd C:\Production_Management_v2
node scripts\backup-db.js
```

`db\backups\projects_manual_YYYYMMDD_HHMMSS.db` が作られる。**このファイルをUSBメモリにコピーする。**

### 4-3. 新PC: DBを配置する

1. 新PCの HiBoard を停止する

```bat
schtasks /end /tn "HiBoard"
taskkill /F /IM node.exe
```

2. フェーズ2の動作確認で作られたテスト用DBを退避する(消さずにリネーム)
   - `C:\Production_Management_v2\db\projects.db` → `projects_test_不要.db` にリネーム
   - `projects.db-wal` / `projects.db-shm` があれば削除してよい(テストDBの作業ファイル)
3. USBメモリの `projects_manual_YYYYMMDD_HHMMSS.db` を `db\` にコピーし、
   **ファイル名を `projects.db` に変更する**
4. 念のため、USBの `db\backups\` の中身も新PCの `db\backups\` にコピーしておく

### 4-4. 新PC: サーバーを起動して中身を確認

```bat
schtasks /run /tn "HiBoard"
```

`http://localhost:3000` を開き、**実際の案件データが入っていること**を確認する。

- 案件一覧に本番の案件が並んでいるか
- 週間スケジュールボードに担当者と予定が出るか
- 顧客台帳(`/customers`)にデータがあるか
- 納品履歴が見えるか

> ここで案件が空・件数が少ないようなら、4-2 のコピーがうまくいっていない。
> **旧PCはまだ何も壊していないので、落ち着いて 4-2 からやり直す。**

### 4-5. 旧PC: Cloudflare Tunnel を止める

**ダッシュボード管理方式(3-2B)の場合** — 管理者コマンドプロンプトで:

```bat
sc stop cloudflared
sc config cloudflared start= disabled
```

**ローカル設定ファイル方式(3-2A)の場合** — サービス化されていれば上と同じ。
コマンドプロンプトで直接動かしていた場合は、そのウィンドウを閉じる。

> ここで**公開フォームが落ちる**。以降の作業を速やかに進める。
> サービスは削除ではなく `disabled`(無効化)にとどめる。切り戻しのため。

### 4-6. 新PC: Cloudflare Tunnel を起動する

**ダッシュボード管理方式(3-2B)の場合** — 管理者コマンドプロンプトで、3-2B でコピーしたコマンドを実行:

```bat
cloudflared.exe service install <ダッシュボードからコピーしたトークン>
```

インストールと同時にサービスが起動する。

**ローカル設定ファイル方式(3-2A)の場合** — まず前面で動作確認してから、サービス化する:

```bat
cloudflared tunnel run hiyoshi-line-webhook
```

`Registered tunnel connection` のようなログが出て接続できたら `Ctrl + C` で止め、管理者コマンドプロンプトでサービス化:

```bat
cloudflared service install
sc start cloudflared
```

> **サービスが起動しない場合:** Windows のサービスは LocalSystem アカウントで動くため、
> `%USERPROFILE%\.cloudflared\` ではなく
> `C:\Windows\System32\config\systemprofile\.cloudflared\` の設定を読むことがある。
> そのフォルダを作り、`config.yml` / `<UUID>.json` / `cert.pem` をコピーしてから `sc start cloudflared` を再実行する。
> (cloudflared は NAS を触らないので、LocalSystem で動いても問題ない)

> **なぜ「旧を止めてから新を起動」なのか:** Cloudflare Tunnel は同じトンネルを複数マシンで同時接続できる(冗長構成)。
> しかし HiBoard のデータベースは1つしかないため、両方を同時に動かすと
> **お客様の注文が2台のPCのDBに振り分けられて散らばる**。必ず旧を止めてから新を起動する。

### 4-7. 疎通確認(ここまでで切り替え完了)

スマホの**モバイル回線**(社内Wi-Fiを切る)で以下を開く。社内LANから見ると社内経路で通ってしまい、トンネルの確認にならない。

- `https://order.kubota-tunnel.com/order` — 注文フォームが表示される
- `https://genpei-hayashi.com` — 選手応援ページが表示される

表示されれば移行成功。フェーズ5の確認に進む。

## 切り戻し手順(うまくいかなかった場合)

**旧PCは何も削除していないので、5分で元に戻せる。** 焦らず以下を実行する。

1. 新PC: HiBoard と cloudflared を止める

```bat
schtasks /end /tn "HiBoard"
taskkill /F /IM node.exe
sc stop cloudflared
sc config cloudflared start= disabled
```

2. 旧PC: cloudflared を戻す(管理者コマンドプロンプト)

```bat
sc config cloudflared start= auto
sc start cloudflared
```

3. 旧PC: HiBoard を起動

```bat
schtasks /run /tn "HiBoard"
```

4. モバイル回線で `https://order.kubota-tunnel.com/order` が開くことを確認

> **注意: 切り替え後に新PCで業務データを入力してから切り戻す場合**、その入力分は旧PCのDBには入っていない。
> 新PCで `node scripts\backup-db.js` を実行してDBを持ち帰り、旧PCの `db\projects.db` と差し替える必要がある。
> **切り替え当日は、疎通確認が終わるまで社員に新PCでの入力をさせない**のが安全。

## フェーズ6: 旧PC(三浦さんのメイン機)の後片付け

**1〜2週間、新サーバー機が安定稼働することを確認してから実施する。**

1. HiBoard の常駐タスクを削除する

```bat
schtasks /delete /tn "HiBoard" /f
```

2. cloudflared サービスを削除する(管理者コマンドプロンプト)

```bat
cloudflared service uninstall
```

3. **フォルダをリネームする** — これが一番大事

`C:\Production_Management_v2` → `C:\Production_Management_v2_移行済み_触らない`

> **理由:** 旧フォルダを残したまま名前も変えないと、誰かが誤って `update.bat` や `npm start` を実行してしまい、
> **「動いているのに誰のデータも増えない幽霊サーバー」**が生まれる。
> 同じPCで2つのDBが並走すると、どちらが本物か分からなくなる。名前を変えておけば事故を防げる。

4. 三浦さんに「このPCは自由に再起動・シャットダウンして構いません」と伝える

## 移行後に変わること・変わらないこと

### 変わらない(社員・お客様への影響なし)

- 公開URL・QRコード・トークン別URL(すべて同じトンネルを引き継ぐため)
- LINE公式アカウントの動作
- **本番反映の手順** — Macで実装 → 社長承認 → main へ push → **新サーバー機で `update.bat` をダブルクリック**
- バックアップの仕組み・復元手順(README「データベースが破損した場合」)

### 変わる

- **社内からのアクセス先** — 新PCのIPアドレスになる
  - 旧PCと同じIPを引き継げれば社員側の変更はゼロ
  - 変わる場合は、社員のブックマークを更新してもらう案内が必要(週次「社内システムお知らせ」に載せるのが良い)
- `update.bat` を実行する場所が新サーバー機になる

## よくあるつまずき

| 症状 | 原因と対処 |
|---|---|
| `npm install` が `node-gyp` エラーで失敗する | Node.js を LTS版に揃える。それでも駄目なら Visual Studio Build Tools(C++デスクトップ開発)を入れる |
| 「📁 参照...」でNASフォルダが出ない | ①`Z:` が割り当てられていない ②タスクを `/rl highest` で作ってしまった(作り直す) ③`.env` のパスがドライブレターと不一致 |
| PC再起動後にサーバーが起動しない | 「ログオン時」トリガーなので誰もログオンしていない。1-2 の自動ログオンを設定する |
| タスク作成が「アクセスが拒否されました」 | 管理者ターミナルで実行していない(管理者はプロンプトが `C:\Windows\System32>` から始まる) |
| PowerShellで `%USERNAME%` が展開されない | PowerShell では `$env:USERNAME` を使う |
| 公開URLが 502 になる | cloudflared は動いているが HiBoard(localhost:3000)が落ちている。`schtasks /run /tn "HiBoard"` |
| 公開URLが繋がらない(DNSエラー) | cloudflared が動いていない。`sc query cloudflared` で状態確認 → `sc start cloudflared` |
| cloudflared サービスが起動直後に停止する | 設定ファイルを LocalSystem のプロフィール(`C:\Windows\System32\config\systemprofile\.cloudflared\`)に置く必要がある。4-6 の注記を参照 |
| 新PCで案件が空・件数が少ない | 4-2 のDBコピーを `.db` 単体コピーで済ませた可能性(WALの未反映分が欠ける)。`node scripts\backup-db.js` でやり直す |
| 公開フォームで「通信エラー」 | 公開ページのAPIが5xxを返している。Cloudflareが5xxを独自エラーページに差し替えるため。サーバーログと `db\crash.log` を確認 |
| 社内画面が公開ドメインで404 | **正常動作**(外部公開ガード)。社内はLAN内IPで開く |
