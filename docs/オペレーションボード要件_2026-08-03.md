# オペレーションボード(山本さん用)要件メモ

作成: 2026-08-03 / 状態: **第1弾を実装済み**(2026-08-03。本番反映は未実施)

## 背景と目的

デザイン担当(鈴木)を制作専任にし、その周辺のオペレーション業務を山本が引き受ける体制へ移行する
(2026-07-27面談・07-28朝会の決定の延長)。現状、案件が「今どこで、誰待ちで止まっているか」は
社長の頭の中にしかなく、放置案件に気づけない。これを画面で見えるようにするのが本要件。

対象は**山本の社内画面**。鈴木のマイスケジュールボード(`/designer/{token}`)とは別画面・別URLで作る。

## 決定事項(2026-08-03 社長)

- 段階は **5段階**
- 鈴木が準備項目を完了したら **②→③へ自動遷移**
- ③は「**山本が確認している**」と「**お客様が確認中**」を明確に分ける
- ①では山本が**大まかなデザインラフまで作成**して鈴木へ渡す
- 既存のかんばん・週間スケジュールボードとは**別画面**

## 1. 5段階の定義

| # | 段階 | コード | 主担当 | 完了の定義(次へ進む条件) |
|---|---|---|---|---|
| ① | ブリーフ作成・ラフ | `BRIEF` | 山本 | 依頼内容が確定し、デザインラフを添えて鈴木へ渡した |
| ② | 制作 | `DESIGN` | 鈴木 | 初稿ができ、提出できる状態 |
| ③ | 確認 | `REVIEW` | 山本 / お客様 | お客様の承認が取れた(修正が必要なら②へ差し戻す) |
| ④ | 入稿・製造 | `PRODUCTION` | 外注(トレス)/ 三浦 | 加工が仕上がった |
| ⑤ | 請求 | `BILLING` | 山本 | 請求書を発行した |
| ⑥ | 検品 | `INSPECTION` | 三浦・渡邉 | 仕上がりのチェックが済んだ |
| ⑦ | 納品 | `DELIVERY` | 山本 | お渡し・発送が済んだ → カードのチェックで `DONE` |

**段階の移動はカードのドラッグ&ドロップで行う**(2026-08-03 追加)。前にも後ろにも動かせるので、
差し戻しも同じ操作。カードを開いてボタンで変更することもできる。

**③の待ち先(ボール)を分ける** — ③のときだけ次の2値を持つ。

| 待ち先 | 意味 | 山本の行動 |
|---|---|---|
| `YAMAMOTO` | 山本がお客様へ確認・催促する番 | 今日やることリストに出る |
| `CUSTOMER` | お客様の返事待ち | リストには出ないが**経過日数を表示**。既定7日超で催促として再浮上 |

## 2. 段階の遷移(自動 / 手動)

| 遷移 | 種別 | トリガー |
|---|---|---|
| ②→③ | **自動** | 鈴木が準備項目「**初稿提出**」をマイボードで完了にした時点。待ち先は `YAMAMOTO` で入る |
| ③→④ | **自動** | 鈴木が準備項目「外注用デザインデータ作成」を完了にした時点 |
| →⑦納品 | **自動** | 既存の納品処理(`POST /api/projects/:id/deliver`)の実行時。**完了にはしない** |
| ⑦→完了 | 手動 | 納品カードのチェックボックス「納品済み・完了にする」 |
| ③内の切替 | 手動 | 山本が「お客様へ送った」を押すと `YAMAMOTO`→`CUSTOMER`。返事が来たら戻す |
| 上記以外 | 手動 | **カードのドラッグ&ドロップ**(前後どちらへも。差し戻しも同じ操作) |

### 実装上の要点(調査結果)

- 鈴木の完了操作は `lib/designer-board.js` の `PATCH /api/designer/:token/items/:id` で、
  既に `syncCaseStatus(item.case_id)` を呼んでいる(l.356)。**ここに段階遷移の処理を足せば自動遷移は実現できる**
- 現在のデザイン担当専用項目(`is_designer_item=1`)は5つ
  = 外注用デザインデータ作成 / 販促物用データ作成 / DTFデータ作成 / 作業指示書作成 / 見積書作成。
  **「初稿提出」に当たる項目がない**ため、②→③のトリガーが作れない。
  → **準備項目「初稿提出」(`FIRST_DRAFT_SUBMIT`, `is_designer_item=1`)を新設する**
  (2026-07-27の面談メモでも「一番効くのは初稿の提出日」としており、方針と一致)
- ①のラフ用に **準備項目「デザインラフ作成」(`DESIGN_ROUGH`)を新設**する。こちらは山本の担当(デザイナー専用項目にはしない)
- 既存の `projects.status`(受注前〜納品済)は**生産工程の軸**で、今回のオペ段階とは別軸。**既存ステータスは触らない**

## 3. データ構造(案)

`projects` に3列を追加(`db/init.js` の「カラムが無ければ追加」方式で後方互換マイグレーション)。

| 列 | 型 | 内容 |
|---|---|---|
| `ops_stage` | TEXT | `BRIEF`/`DESIGN`/`REVIEW`/`PRODUCTION`/`BILLING`/`DONE`。既定 `BRIEF` |
| `ops_wait_on` | TEXT | `YAMAMOTO`/`CUSTOMER`。③以外はNULL |
| `ops_stage_since` | TEXT | 現在の段階に入った日時。経過日数の表示に使う |

準備項目マスターに2件追加(冪等シード)。

- `DESIGN_ROUGH` デザインラフ作成(`is_designer_item=0`)
- `FIRST_DRAFT_SUBMIT` 初稿提出(`is_designer_item=1` — 鈴木のマイボードに自動で入る)

**「初稿提出」は案件登録時に自動付与する**(2026-08-03 社長判断)。対象は社内デザイン案件、または
デザイナー専用項目が1つでも選ばれた案件。手動チェック方式だと入れ忘れたときに②→③の自動遷移が
起きず、案件が制作段階に居座ったまま誰も気づけないため。

## 4. 画面(`/ops` 想定)

社内画面。トークン不要。ヘッダーは `ui.js` の共通ナビに追加する(`navDaily`)。

**上段: 今日やること** — 次の条件に当たる案件を行で並べ、各行に操作ボタンを置く。

- 段階①の案件(ブリーフ・ラフが未完了)
- 段階③かつ待ち先が `YAMAMOTO` の案件
- 段階③かつ待ち先が `CUSTOMER` で経過7日超(催促)
- 段階⑤の案件(請求未発行)
- 期限が近い/超過している案件を上に出す

**下段: パイプライン** — 5段階を列にしたカード表示。カードには案件名・顧客・納期・経過日数・待ち先バッジ。
カードをクリックすると既存の案件詳細(`js/case-detail.js`)を開く。

**掲載範囲**(2026-08-03 変更): 案件登録時に**「デザイン案件全般として管理する」をチェックした案件のみ**
(`projects.is_design_ops = 1`)。当初は準備項目から自動判定していたが、デザインデータを作るだけの
通常のプリント案件まで載って山本が見るべき案件が埋もれるため、明示的なチェック方式に変更した。
`ops_stage = 'DONE'` は既定で非表示(切替で表示可)。

**画面名**: 「オペレーション」→「🗂 デザイン案件全般」(URLは `/ops` のまま)。

## 5. 段階的な実装計画

| 段階 | 内容 | 判断 |
|---|---|---|
| **第1弾** | 上記1〜4(可視化と段階管理)のみ | まずここまで作り、山本が1〜2週間使う |
| 第2弾 | 対外メール・書類の**下書き生成** | 山本が実際に何のメールを何回書いているかを見てから作る |

**下書き生成についての方針(第2弾)**: 初回は「画面に文面を表示 → 山本がコピーして自分のメーラーで送る」方式を推奨する。
Gmailの下書きを自動生成する方式は、誤送信リスクと実装量が増えるため、運用が固まってから検討する。

## 6. 確認事項の結論(2026-08-03)

1. 催促の日数 → **7日**で実装(`.env` の `OPS_CUSTOMER_REMIND_DAYS` で変更可)
2. デザインラフの置き場 → **案件への添付方式**(社長判断)。
   鈴木さんが会社のNASにアクセスできないため、NASではなくサーバー内(`data/rough_uploads/`)に保存し、
   デザイナーのマイスケジュールボードからトークン付きURLで開けるようにした
3. 山本の従業員登録 → **登録済み**(`employees` に「山本 勇一郎」あり。追加作業なし)
