### 常駐化でNSSMを却下した理由（重要な経緯）

Windowsサービス（NSSM）だと LocalSystem 権限で動くため**NASの割り当てドライブ（Z:）が見えず**、
デザインデータ閲覧・注文画像保存・NASバックアップの計4か所が壊れる。
同じ理由でタスクスケジューラでも `/rl highest` は付けない（管理者権限プロセスからも割り当てドライブが見えない）。

設定時のつまずき: PowerShell では `%USERNAME%` が展開されない（`$env:USERNAME` を使う）／
管理者でないと「アクセスが拒否されました」。→ 手順は `docs/Windowsサービス化手順.md` に反映済み。

### デザイン案件全般ボード `/ops`（2026-08-03実装、同日に名称と対象範囲を変更）

デザイン担当（鈴木さん）を制作専任にし、その前後のやりとりをオペレーション担当（山本さん）が回す体制への対応。
要件は `docs/オペレーションボード要件_2026-08-03.md`。

- **既存の `projects.status`（生産工程の軸）は触らず、別軸で持つ**: `ops_stage`（BRIEF/DESIGN/REVIEW/PRODUCTION/BILLING/DONE）・
  `ops_wait_on`（REVIEW段階のみ YAMAMOTO / CUSTOMER）・`ops_stage_since`（滞留日数の起点）
- **③確認は4ステップ**（`REVIEW_STEPS`。2026-08-03に2値→4ステップへ作り替え、社長指示）。
  実際のやりとりの順に SEND（お客様へ確認連絡）→ REPLY_WAIT（返事待ち）→ ADJUST（位置・大きさの調整）
  → FINAL_WAIT（最終確認の返事待ち）→ OKで④入稿・製造。各ステップは `ball` を持ち、
  `US`（社内の番）は「今日やること」に出し、`CUSTOMER`（返事待ち）は既定7日
  （`OPS_CUSTOMER_REMIND_DAYS`）を過ぎたときだけ催促として再浮上する。
  ステップを切り替えたときも `ops_stage_since` を打ち直す（そのステップに入ってからの日数を見たいため）。
  旧値 YAMAMOTO/CUSTOMER は `db/init.js` のマイグレーションで SEND/REPLY_WAIT へ読み替える
- **進行タイプ `projects.ops_flow`**（2026-08-03追加）: `FULL`（加工まで・標準）/ `SUBMIT_END`（紙媒体・入稿で完了）。
  「鈴木さんで始まり鈴木さんで終わる」紙媒体案件のための流れ。登録フォームのラジオで選ぶ。
  SUBMIT_END は**登録時に制作（DESIGN）から始まり**（ブリーフ・ラフを飛ばす）、
  準備項目**「入稿完了」（`SUBMISSION_COMPLETE`・デザイナー専用・SUBMIT_ENDにだけ自動付与）**を
  デザイナーが完了すると**「請求」へ自動遷移**する（検品・納品は通らない）。
  請求カードに「請求済み・完了にする」チェックが出て、そこで完了。カードには 📄 バッジ。
  鈴木さんは社内画面(/ops)を触れないため、本人のマイボードの完了操作だけで締められるのが設計意図
- **紙媒体の工程別納期 `projects.first_draft_due` / `submission_due`**（2026-08-03追加）:
  案件全体の納期だけでは鈴木さんが「初稿はいつまで/入稿はいつまで」を判断できないため、
  紙媒体案件では工程ごとに納期を持たせる。**マイスケジュールボードの各カードは
  この日付を「初稿の納期」「入稿の納期」として表示する**（`itemDue()`。未設定なら案件の納期）。
  デザイン案件全般ボードのカードにも「初稿 8/10 / 入稿 8/22」を並べる
- **紙媒体でカードが2枚並ぶ問題の解消**（2026-08-03）: 登録直後に「初稿提出」と「入稿完了」の
  2枚がマイスケジュールボードに並んで見づらかったため、**「入稿完了」は入稿の出番
  （`ops_stage` が PRODUCTION / BILLING）になるまで出さない**（`SUBMISSION_ITEM_SQL`）。
  制作〜確認の間は初稿提出だけ、入稿・製造に入ったら入稿完了だけが見える
- **紙媒体の出どころ `projects.paper_source`**（2026-08-03追加）: `HIYOSHI`（弊社からの依頼）/
  `CARVE`（鈴木さんがCARVEで受けている案件）。`ops_flow='SUBMIT_END'` のときだけ意味を持ち、
  登録フォームでは紙媒体を選んだときだけラジオが出る（`app.onOpsFlowChange()`）。
  **CARVE案件はイレギュラーなので、ボードのカードに紫の枠（`.is-carve`）とバッジを付けて目立たせる**
- **バトンタッチ自動通知**（2026-08-03・`lib/ops-notify.js`）: 山本さん⇔鈴木さん間の
  「ステータス変更したのでよろしく」「完了したのでよろしく」という手動報告の置き換え。
  `setStage` で段階が実際に変わった瞬間に Google Chat の共有スペースへ自動投稿する
  （制作へ渡した→鈴木さんへ / 初稿提出→山本さんへ / 差し戻し→鈴木さんへ /
  紙媒体の入稿依頼→鈴木さんへ / 入稿完了→山本さんへ など。完了も記録として流す）。
  **同じ段階内の操作（確認4ステップの切り替え等）では送らない**（通知疲れ対策）。
  設定は `.env` の `OPS_NOTIFY_GCHAT_WEBHOOK`（Google Chat スペースの Webhook URL）。
  未設定なら何もしない（SMTPと同じ方針）。通知失敗は業務処理を止めず、ログだけ残す。
  通知文に顧客名は入れない（案件名＋アイテム名のみ）
- **デザイナーのマイスケジュールボードは「入稿・製造」の手前まで**（2026-08-03 社長指示）。
  `lib/designer-board.js` の scheduled / unscheduled 両方に
  `(p.is_design_ops = 0 OR p.ops_stage IN ('BRIEF','DESIGN','REVIEW') OR (p.ops_flow='SUBMIT_END' AND p.ops_stage='PRODUCTION'))`
  を掛けている（紙媒体タイプは入稿作業自体がデザイン担当の仕事なので入稿・製造の間も表示し続ける）。
  入稿が済んだ案件の作業はデザイン担当の手を離れているため、完了チェックが残っていてもボードから外す。
  ボードに載せていない案件（`is_design_ops = 0`）は段階の概念がないので従来どおり全部出す
- **準備項目を2つ新設**: `FIRST_DRAFT_SUBMIT`（初稿提出・デザイナー専用項目）と `DESIGN_ROUGH`（デザインラフ作成）。
  既存のデザイナー専用5項目は「見積書作成」等を含み初稿の完了を表せなかったため、②→③のトリガー専用に追加した
- **デザイン案件全般の準備項目は全部デザイン担当へ**（2026-08-03 社長指示・`registerPreparationItems()`）。
  `is_design_ops = 1` の案件は、選ばれた準備項目の種類を問わず**全項目をデザイン担当へ割り当てる**
  （通常案件は従来どおりデザイナー専用項目のみ）。さらに**準備項目も担当者も未選択のまま登録しても
  ボードとマイスケジュールボードに必ず出る**ように、フロント側は `is_design_ops` が立っていれば
  準備項目が空でも `POST /api/projects/:projectId/preparation-items` を呼ぶ
  （サーバー側が「初稿提出」等を用意する）。一覧の「🗂 全般へ」でも同じ処理を通す
  （`registerOpsBoardRoutes` に `deps.registerPreparationItems` を注入）。
  あとから切り替えた案件は、担当が空の未完了項目をデザイン担当へ寄せ直す
- **「初稿提出」は案件登録時に自動で足す**（`POST /api/projects/:projectId/preparation-items`）。
  対象は社内デザイン案件、またはデザイナー専用項目が1つでも選ばれた案件。
  手動チェックのままだと入れ忘れたとき②→③の自動遷移が起きず、**案件が制作段階に居座っても誰も気づけない**ため（2026-08-03 社長判断）
- 自動遷移は `lib/designer-board.js` の準備項目更新（`syncCaseStatus` の隣）と `POST /api/projects/:id/deliver` にフックしている。
  **完了を取り消しても段階は巻き戻さない**（提出済みのものを機械的に戻すと実態と合わなくなるため、戻す操作は画面から手動）
- **デザインラフはNASに置かない**。鈴木さんは会社のNASにアクセスできないため `data/rough_uploads/`（`ROUGH_UPLOAD_PATH` で変更可・git管理外）に
  保存し、社内は `/api/ops/rough/:id/file`、デザイナーは `/api/designer/:token/rough/:id` から配信する。
  後者は「その案件に本人の準備項目があること」を条件にしており、他案件のIDを入れても404
- **掲載対象は `projects.is_design_ops` フラグで決める**（2026-08-03 社長判断で変更）。
  当初は「デザイン系の準備項目を持つ案件」を自動判定していたが、デザインデータを作るだけの通常のプリント案件まで
  載って山本さんが見るべき案件が埋もれるため、**案件登録画面のチェックボックス「デザイン案件全般として管理する」**を
  明示的に押した案件だけを対象にした。チェックは新規案件モーダルと受注候補の確定画面の両方にあり、編集で後から付け外しもできる。
  導入時のマイグレーションで、旧条件に当てはまる未完了案件へ1回だけフラグを立てている（既存の表示が消えないようにするため）
- 画面名は「オペレーション」→**「🗂 デザイン案件全般」**に変更（URLは `/ops` のまま）
- **段階を5→7に拡張**（2026-08-03 社長要望）: 請求のあとに **検品・納品** を追加。
  納品カードのチェックボックスで完了（DONE）にする運用にしたため、
  `POST /api/projects/:id/deliver` の遷移先を請求→**納品**に変更した（`markDeliveredStage`）。
  納品処理で自動的に完了にはしない — 請求・検品が済んだかを山本さんが締める運用のため
- **段階の移動はカードのドラッグ&ドロップ**。前にも後ろにも動かせる（差し戻しも同じ操作）。
  段階が7つあるので列は横スクロール（`.ops-pipeline` を `display:flex` + `overflow-x:auto`。
  ページ全体は横に伸びない）。スマホ幅では縦積みに切り替える
- 「今日やること」は行ではなく**カード**表示（案件名・顧客・やること・納期・段階バッジ）
- **掲載の付け外しは `PATCH /api/ops/cases/:id/membership` の1本**（`{include: true|false}`）。
  外す = ボードのカード右上「✕」、載せる = HiBoard一覧ビューの行にある「🗂 全般へ」ボタン
  （載っている案件では「🗂 全般から外す」に変わり、`btn-primary` で強調される）。
  `is_design_ops` を切り替えるだけで**案件そのものは削除しない**。確認ダイアログでも
  「案件そのものは消えません」と明示している（案件の削除は一覧ビューから行う）
- **アイテム名 `projects.item_name`**（2026-08-03追加）: 何を作る案件かをカードで分かるようにする自由入力。
  新規案件モーダルと受注候補の確定画面の両方に入力欄がある。ボードの表示は
  ①`item_name` → ②`case_items` の先頭アイテム（カテゴリのコードを日本語へ直し「ほかN点」を付ける）の順で決める。
  Web注文フォーム由来の案件は②で自動的に出るので、手入力は不要

## 2026-07-30 納品済み案件の準備項目が残り続ける問題を修正

### 症状

納品済みの案件なのに、準備項目のタスクがいつまでも残っていた(社長report)。

### 原因

`POST /api/projects/:id/deliver` は `case_time_allocations`(作業ブロック)は削除していたが、
**`case_preparation_items` は未完了のまま放置していた**。項目が「まだやること」として残るため、
`status != '完了'` を条件にしている次の3か所に永久に出続けていた。

1. **デザイナーのマイスケジュールボード「日付が未定のタスク」**(`lib/designer-board.js` の `unscheduled` クエリ)
   … 案件ステータスの条件が無く、納品済みでも本人のやることとして残り続ける。ここが一番影響が大きかった
2. **勤務時間編集モーダルの「準備項目タスクの割り当て」候補プルダウン**(`assignablePrepItems` の繰り越し分)
3. 週間ボードの準備項目リストの繰り越し … 表示は `PREP_LIST_HIDDEN_PROJECT_STATUSES` で除外されていたが、データは残っていた

### 対応(社長方針: 納品したものは未完了のタスクが残っていても全て完了とみなす)

- **納品時に未完了の準備項目をまとめて完了にする**(deliver のトランザクション内)。
  これで上記3か所すべてが同時に解決する(どれも `status != '完了'` で絞っているため)
- **既存データのバックフィル**(`db/init.js`、起動時1回・冪等)。
  納品済み案件に残っていた未完了項目を完了にする。`completed_at` は納品日を使う
- 保険として表示側にもガードを追加: 繰り越しAPI(`overdue_before`)と
  デザイナーボードの `unscheduled` から `p.status = 'COMPLETED'` を除外

`syncCaseStatusForPreparationItems()` は WAITING↔PREP_COMPLETE しか動かさないので、
完了にしても案件ステータスが COMPLETED から巻き戻ることはない(検証済み)。

### あわせて修正: 案件別消化率の表示がはみ出していた

`.sb-progress-item` の数値列が固定140px + `white-space: nowrap` で、
`2h / 10.0h（見積もり参考値）（20%）` が枠外に飛び出していた。

- 列幅を `minmax(0, 220px) minmax(80px, 1fr) auto` にして内容に合わせて伸ばす

## 2026-08-07 マイスケジュールに出す案件を「制作」段階のみに絞る

社長指示。デザイン案件全般ボードに載せた案件は、鈴木さんのマイスケジュールに
**「② 制作」の段階のあいだだけ**出すようにする。ブリーフ・ラフ(山本さんの番)と
確認(山本さん↔お客様)の間はデザイン担当の番ではないため、カードごと引っ込める。

### 仕様

`lib/designer-board.js` の絞り込み条件を `ops_stage IN ('BRIEF','DESIGN','REVIEW')` から
`ops_stage = 'DESIGN'` に変更(定数名も BEFORE_PRODUCTION_SQL → DESIGNER_TURN_SQL)。
例外の2つは**そのまま維持**する(2026-08-07 社長判断)。

- **全般ボードに載せていない案件(is_design_ops=0)は従来どおり全部出す** —
  通常のプリント案件のデザイン作業(外注用デザインデータ作成 等)と社内デザイン案件が
  鈴木さんの画面から消えてしまうため。段階の概念を持たない案件なので絞り込みの対象外
- **紙媒体(SUBMIT_END)の「入稿・製造」は残す** — 入稿作業自体がデザイン担当の仕事。
  ここを絞ると「入稿完了」のカードが永久に出ず、本人が請求へ進める操作ができなくなる

### 運用上の注意(仕様変更で新しく効いてくる点)

- 初校提出を完了すると自動で「確認」へ進むため、**その案件のカードはその場で消える**
- **修正で戻すときは「段階を制作に戻す」＋「初校提出の完了チェックを外す」の2つが必要**。
  完了した項目は元から表示対象外なので、段階を戻すだけではカードが出てこない

### 実装

- `lib/designer-board.js` … DESIGNER_TURN_SQL(scheduled / unscheduled の両クエリで使用)
- `public/manual.html` … 「デザイン担当の画面に出る作業」を書き換え
- `docs/designer-board/デザイナーボード運用マニュアル.html` … 画面の説明に追記
- `docs/案件の振り分け条件_現状整理.html` … 新規作成した振り分け資料を新仕様に更新(A4 3ページ)

### 検証

開発機でテスト案件8件を段階ごとに作り、マイスケジュールAPIの返り値で確認。

| 案件 | 段階 | 結果 |
|---|---|---|
| 全般ON / FULL | ブリーフ・ラフ | 出ない |
| 全般ON / FULL | 制作 | 出る |
| 全般ON / FULL | 確認 | 出ない |
| 全般ON / FULL | 入稿・製造 | 出ない |
| 全般ON / 紙媒体CARVE | 制作 | 出る(初校提出) |
| 全般ON / 紙媒体CARVE | 確認 | 出ない |
| 全般ON / 紙媒体CARVE | 入稿・製造 | 出る(入稿完了) |
| 全般OFF / 通常プリント | (段階なし) | 出る(見積書作成・初校提出) |

あわせて、初校提出の完了 → 自動で確認へ進みカードが消えること、段階を制作に戻しただけでは
出てこず完了チェックを外すと再び出ることも確認。テスト案件・検証用リンクは削除済み。

## 2026-08-07 修正往復の仕組み: 「✏️ 修正で鈴木さんへ戻す」ボタン+修正回数バッジ

社長相談。デザインは一度で決まらず「提出→お客様確認→修正指示→再提出」を数回繰り返してから
確認(プリント位置等)に進むのが実態。この往復を両ボードに取り入れたい。

### 設計判断

新しい段階は増やさない。段階の軸は既に「いま誰の番か」を表しており、修正往復は
「確認 ⇄ 制作」の行き来として表現できる。問題は (1)戻す操作が2段階(段階戻し+チェック解除)で
忘れやすい、(2)何往復目か・指示内容がどこにも残らない、の2点なので、そこだけを解決する。
「確認段階の中に修正中ステップを足す」案は、段階=確認なのに実作業者=鈴木さんというねじれと
マイスケ表示条件の複雑化を招くため不採用。

### 仕様

- `projects.design_revision_round`(既定0)・`design_revision_note` を追加
- **`POST /api/ops/cases/:id/return-for-revision`**(body: note 任意500字) — 1クリックで:
  ①段階を「制作」へ(バトンタッチ通知は setStage 経由で自動) ②完了済みの「初校提出」を
  未着手に戻し予定日クリア(未完了なら触らない) ③回数+1・メモ保存(上書き。履歴は残さない=社長判断)
  ④校正バッジを「修正」に。全般ボード外の案件(is_design_ops=0)は400
- **全般ボード**: 確認段階のカードモーダルに「✏️ お客様から修正指示が来たとき」欄
  (直近の指示表示+メモ欄+ボタン、confirm付き)。カード・モーダル要約に「🔁 修正◯回目」バッジ
- **マイスケ**: チップ名の横に「🔁 修正◯回目」、メタ行に「✏️ 修正指示: …」(いずれも round>0 のみ)
- 鈴木さんが再提出(初校提出を完了)すると既存の自動遷移で「確認」へ。何往復でも回る

### 実装

- `db/init.js` … design_revision_round / design_revision_note 列追加(冪等)
- `lib/ops-board.js` … return-for-revision API・ボードAPIに2列追加
- `lib/designer-board.js` … 3クエリに2列追加・itemToJson に revision_round / revision_note
- `public/js/ops-board.js`・`public/ops-board.html`・`public/styles/ops-board.css` … ボタン・バッジ・欄
- `public/js/designer-board.js`・`public/designer-board.html` … チップのバッジ+指示メモ表示
- `public/manual.html`・デザイナーボード運用マニュアル・案件の振り分け条件_現状整理.html … 説明更新
  (「修正で戻すときは2段階の手作業が必要」の記述はボタン方式に差し替え)

### 検証

開発機で全般ボード案件を作り、初校提出完了→確認→修正戻し→再提出→再度修正戻し の2往復+
UIボタンからの3往復目を実施。①戻すたびに 段階=制作/初校提出=未着手/予定日=NULL/round+1/
proof_stage=REVISION が一括反映 ②マイスケのチップに「🔁 修正2回目」+指示メモ+校正バッジ「修正」
③全般ボードのカード・モーダルにバッジと直近指示 ④再提出で確認へ自動遷移(roundは維持)
⑤全般ボード外の案件=400・存在しない案件=404 を確認。テスト案件・検証用リンクは削除済み。
